`TRCC.LCD` is a namespace that did not exist in the release the rest of these
audits describe. `FormLCD.cs` is 5,082 lines of it — a host form parallel to the
`TRCC.CZTV/FormCZTV.cs` in [`BEHAVIOR_FORMCZTV.md`](BEHAVIOR_FORMCZTV.md), with
its own `FormCZTVInit` and its own theme I/O.

**It is not a second encoder.** `ImageToJpg`, `ImageTo565` and `GetEncoder` do
not exist in this file; it never builds a wire frame. What it has instead is the
shared-memory pair — `InitMemorySize`, `ReadShareMemory`, `WriteShareMemory`,
`SetConfigurationToMemory`, `GetConfigurationToMemory` — and it launches the
helper executable `LCD\TRCCLCDAPP.exe`, which owns the wire. This is the second
of the two discovery worlds `AUDIT_DISCOVERY.md` describes: in-process HID on
one side, an external process fed through a memory-mapped file on the other.

The device it serves is a specific one. `FormCZTVInit` walks `Screen.AllScreens`
and counts only monitors whose bounds are exactly **2560×720 or 720×2560**,
taking the `myDeviceCount`-th of them for its geometry, and its remaining
branches key on **`fbl == 257`** — the shared-memory RGB LCD that
`AUDIT_DISCOVERY.md` records as ID `257` (`USB_ID1_1`), added by
`RGB_ADD_Device` rather than by HID enumeration. So this host drives an
ultrawide strip panel that presents to Windows as a monitor, not a panel we
build frames for.

**What that means for the port:** nothing in our render path is contradicted by
this file, which is the useful negative result — the encoder conclusions in
`AUDIT_LCD_PIPELINE.md` stand as the only ones. What it does describe is a
device class we do not support at all, and would reach through a completely
different seam if we ever did.

**Read this doc as a map, not as settled protocol.** It is the first pass over a
file nothing had read.

Companion: [`AUDIT_LCD_PIPELINE.md`](AUDIT_LCD_PIPELINE.md) owns the
compose→rotate→wire model recovered from `FormCZTV`; entries here that touch the
same ground cross-reference it rather than restating it.

Source policy applies: facts, never pasted source — see
[`AUDIT_INDEX.md`](AUDIT_INDEX.md#source-policy--facts-not-source-text).

- `ReadFileTheme` (FormLCD.cs:1081) — rebuilds the local theme list from disk. Clears `themeArray`, enumerates the subdirectories of `fileThemeDir` (= `USBLCD\Theme` + `ThemeML`), and orders them by: entries named in the priority list `Theme1`, `Theme2`, `Theme3`, `Theme4`, `Theme5` first (descending on membership), then by index within that list, then alphabetically by name — so the five shipped themes always lead, in numeric order, and user themes follow alphabetically (FormLCD.cs:1086-1089). Key branches: `directory contains >= 2 files -> added to themeArray`; `directory contains fewer than 2 files -> Directory.Delete(..., recursive: true)`, i.e. loading the theme list silently and permanently destroys any theme folder holding 0 or 1 file (FormLCD.cs:1092-1099); `bl == false` -> `ReadFileThemeSub` returns immediately, so the directory scan and the deletion still happen but the persisted `Theme.dc` selection is not re-read. Porting caveat: the file-count probe concatenates `fileThemeDir` with the `DirectoryInfo` object (its string form), whereas the list stores `.Name` — the two are not built the same way.
- `FontToBytes` (FormLCD.cs:376) — serialises a font to the blob embedded in shared-memory slot 1 (see `SetConfigurationToMemory`, FormLCD.cs:590). Field order, written through a UTF-8 `BinaryWriter`: family name as a .NET length-prefixed string (7-bit-encoded varint byte count, then UTF-8 bytes), size as a 4-byte little-endian float, `FontStyle` as int32, `GraphicsUnit` as int32, `GdiCharSet` as a single byte. Key branches: `font == null -> zero-length array`; `font.Name == null -> empty string written` (the varint length prefix is still emitted). Total blob length is stored as a 16-bit little-endian count at element offset +18 by the caller, so a font blob must stay under 65536 bytes.
- `BytesToFont` (FormLCD.cs:397) — inverse of `FontToBytes`; reads name (varint-length-prefixed UTF-8 string), size (float32), `FontStyle` (int32), `GraphicsUnit` (int32), `GdiCharSet` (byte) in that order and constructs the font from all five. Key branches: `data == null or data.Length == 0 -> SystemFonts.DefaultFont`; `any read or construction throws -> SystemFonts.DefaultFont` (so a truncated or foreign-endian blob degrades silently to the system default rather than failing loudly).
- `ClearMemoryMy` (FormLCD.cs:1196) — public static, takes a `memory` threshold defaulting to 20, and has a completely empty body: it does nothing at all. Dead API kept for call-site compatibility; a port should not implement it. No branches.
- `ClearMemorySelf` (FormLCD.cs:1200) — public static, takes a `memory` threshold defaulting to 1000, empty body, does nothing. Same dead-API situation as `ClearMemoryMy`; note the two differ only in their default threshold, and neither uses it. No branches.
- `ClearMemoryAll` (FormLCD.cs:1204) — the one memory routine that is not empty. Forces `GC.Collect` then `GC.WaitForPendingFinalizers`, then enumerates **every process on the machine** via `Process.GetProcesses()` and calls the psapi `EmptyWorkingSet` on each one's handle — not just this app's. Key branches: `EmptyWorkingSet or handle access throws for a process -> caught per-process and ignored, loop continues` (which is the normal case for processes the user cannot open). Has no Linux equivalent and no functional purpose for a port; it is a Windows working-set-trimming hack.
- `CloseShareMemory` (FormLCD.cs:346) — disposes the `MemoryMappedFile` handle, then scans every running process and kills any whose `ProcessName` contains `lcdAppName`. Key branches: `process.ProcessName contains lcdAppName -> process.Kill()`; `any exception during enumeration or kill -> swallowed, method returns`. Load-bearing defect for a porter: `InitMemorySize` (FormLCD.cs:319) overwrites `lcdAppName` with `LCD\TRCCLCDAPP.exe` before this ever runs, while `Process.ProcessName` yields a bare name with no directory and no extension — the `Contains` test can therefore never match after initialisation, so the spawned helper process is never actually terminated and survives the form. Compounding it, `InitMemorySize` re-prefixes the same field on every call.
- `EmptyWorkingSet` (FormLCD.cs:1194) — not a managed method: a private static P/Invoke declaration importing `EmptyWorkingSet` from `psapi.dll`, taking a process handle and returning an int. Its only caller is `ClearMemoryAll` (FormLCD.cs:1214). Declared alongside `SetProcessWorkingSetSize` from `kernel32.dll` (FormLCD.cs:1191), which is declared but never called anywhere in the read range. Behaviour is the Win32 API's; no managed body exists to describe. No branches.
